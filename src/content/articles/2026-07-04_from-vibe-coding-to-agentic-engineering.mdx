AI models have come a long way. They can now perform many engineering tasks
that used to require a developer sitting in front of an IDE: reading code,
editing files, writing tests, explaining failures, searching documentation, and
proposing implementation plans.

But there is still a hard limit: they do what you ask, not necessarily what you
meant.

That is the mindset shift. Do not treat a language model as a complete engineer
who has been in your company for years, understands the product, knows the
architecture, remembers every business rule, and can infer what you forgot to
say. A better mental model is a very fast new expert employee: strong general
knowledge, strong execution speed, weak local context, no real ownership, and no
reliable judgment unless you provide the information and constraints they need.

With current models, the work is no longer only about knowing the answer
yourself. It is about asking for the right work, giving the right context, and
verifying the result.

Models do not think like humans. They imitate reasoning patterns, but they do
not share your assumptions. They do not naturally understand what is "between
the lines." If you omit important context, they will usually still answer,
because answering is what they are optimized to do.

Agentic engineering is the discipline of making that behavior useful in real
software work. It is the move from casual vibe coding to a structured way of
delegating work to agents: clear context, clear plans, controlled tools,
repeatable workflows, and verification loops.

## Context engineering

Models can perform very well when they know what to do, where to do it, and
which information matters. That is why context is one of the most important
resources in agentic engineering.

Context engineering is the practice of deciding what information the model sees,
when it sees it, and how that information is structured.

The goal is not to give the model everything. The goal is to give it the minimum
complete context required to do the job well.

If you want an LLM to perform the right action in the right place and produce
the result you actually want, you need to be intentional about context.

Everything you give to the model can influence its answer. Relevant information
helps. Irrelevant information can contaminate the reasoning. Old requirements,
noisy logs, unused tool descriptions, stale files, and unrelated documentation
can all compete with the real task.

That means more context is not always better.

Even if a model technically supports a very large context window, the useful
part of that window is smaller in practice. Long context increases cost,
latency, and the chance that the model pays attention to the wrong thing. A
model with a clean 20,000-token context can often perform better than the same
model with 150,000 tokens of mixed logs, old discussion, unrelated files, and
tool descriptions.

The practical rule is simple:

> Give the model everything it needs, but nothing that only makes the session noisy.

## High-level guidelines

There are several ways to reduce context size without starving the agent.

Start new sessions for new tasks. A long conversation accumulates assumptions,
decisions, dead ends, and outdated instructions. When the task changes, a fresh
session with a short summary is often better than dragging the whole history
forward.

Use sub-agents for specialized work. A main agent does not need every tool,
every document, and every workflow in its own context. A specialized sub-agent
can handle one bounded task with only the tools and instructions it needs.

Keep repository summaries available. A short, accurate summary of the repository
structure, commands, architectural conventions, and ownership boundaries can
save the model from repeatedly scanning the whole codebase.

Prefer focused file reads over broad ingestion. Ask the agent to inspect the
files directly related to the task, then expand only when necessary.

Summarize long outputs before continuing. Logs, test failures, and command
outputs should be reduced to the important evidence: the failing command, the
error, the stack trace, the changed files, and the likely affected area.

## Minimal project instructions

Project instruction files such as `AGENTS.md`, `CLAUDE.md`, or similar guidance
files should be short and specific.

There is no need to explain that a repository is TypeScript, Python, .NET, Java,
or another common stack if the model can infer that from the files. There is
also no need to include generic advice such as "write clean code" or "follow
best practices." Modern models already know those words, and they are too vague
to be useful.

What the model does not know is your local reality:

- how the codebase is organized
- which commands validate the work
- which directories are generated and should not be edited
- which architectural boundaries must not be crossed
- which internal APIs or patterns are preferred
- which files contain source-of-truth business rules
- what to do before and after each task

A good instruction file is a map, not a software engineering textbook.

```md
# Agent Instructions

- API route handlers live in `src/server/routes`.
- Business logic belongs in `src/domain`.
- Do not query the database directly from route handlers.
- Shared UI components live in `src/components/common`.
- For focused validation, run `npm run test -- <package>`.
- Before changing a public API, update the related contract tests.
```

This kind of file gives the agent information it cannot reliably guess.

## Disable tools when they are not needed

MCP tools are powerful, but they are not free.

Tool definitions are added to the agent's context. That means every enabled MCP
server can increase token usage, add latency, and distract the model with tools
it may never need for the current task.

If a task is purely local code editing, the agent may not need access to Jira,
Slack, Confluence, GitHub, cloud dashboards, or deployment systems. Keeping
those tools enabled by default can make the main agent heavier and less focused.

Disable tools that are not required for the task. When possible, give agents the
smallest set of tools that can complete the work.

Another option is to use specialized sub-agents. For example, the main coding
agent can stay lightweight, while a documentation sub-agent has access to
Confluence, or a delivery sub-agent has access to CI/CD tools. The main agent
calls the specialist only when that information is needed.

## Compress the conversation

The less useless text you carry forward, the less context pollution you create.

Instead of long explanations, remove filler, pleasantries, hedging, and
unnecessary words when the agent does not need them.

Normal:

```text
The issue is likely caused by the authentication middleware checking token
expiration incorrectly. I recommend updating the comparison operator and then
running the related tests.
```

Compressed:

```text
Bug in auth middleware. Token expiry check wrong. Fix comparison. Run auth tests.
```

The important rule is that technical information must stay exact. Code,
commands, API names, and error messages should not be damaged by compression.
When safety or clarity matters, switch back to normal language.

Tools such as [`rtk`](https://github.com/rtk-ai/rtk) apply the same idea to
command output by filtering, grouping, truncating, and deduplicating logs before
they enter the model context.

## Use sub-agents to avoid the God Agent

Sub-agents solve the "God Agent" anti-pattern.

A God Agent has too many tools, too many instructions, too many
responsibilities, and too much context. It can answer many things, but it
becomes expensive, slow, hard to debug, and more likely to make mistakes.

Sub-agents split work into specialized modules. Each one has a narrow
responsibility, a small context, and the minimum tools needed for the job.

Use sub-agents when a task naturally separates into different kinds of work:

- code implementation
- test generation
- documentation lookup
- CI/CD investigation
- security review
- database migration review
- product requirement clarification
- release note generation

A simple pattern is to use a lightweight router agent. The router reads the user
request, identifies the type of work, and delegates it to the right specialist.

The important rule is context economy:

> Each sub-agent should receive only the tools, instructions, and history required for its specific job.

This improves accuracy, lowers cost, and makes failures easier to debug.

## Plan the work

Good agentic engineering starts before code generation.

Most bad AI coding outcomes are not caused by weak syntax generation. They are
caused by weak task definition. The agent was asked to "build the feature"
without a precise definition of the feature, the constraints, the affected
files, the expected behavior, or the verification path.

Planning gives the model a smaller target.

Before delegating implementation, define:

- the problem
- the user-visible behavior
- the non-goals
- the affected modules
- the constraints
- the acceptance criteria
- the test strategy
- the rollback or review concerns

For small tasks, this can be a few bullets. For larger work, it should become a
specification.

## Spec-driven development

Spec-driven development means writing a clear specification before
implementation, then using that specification as the contract for the work.

In an agentic workflow, the spec is especially important because it becomes the
agent's source of truth. It prevents the model from inventing requirements,
guessing hidden constraints, or optimizing for a vague interpretation of the
task.

A useful spec usually includes:

- background and problem statement
- current behavior
- desired behavior
- user stories or use cases
- explicit non-goals
- technical constraints
- affected systems
- data model changes
- API or UI changes
- acceptance criteria
- test plan
- rollout or migration notes

The spec does not need to be huge. It needs to be clear enough that a new
engineer, or an agent, can implement the work without repeatedly guessing.

The practical workflow:

```text
idea -> plan.md -> todo.md -> implementation -> tests -> review
```

`plan.md` explains what should be built and why.

`todo.md` breaks the plan into small implementation steps.

The agent works through the todo list one item at a time, updating the status as
it goes. This keeps the work inspectable and reduces the chance that the model
makes a large uncontrolled change.

## Agentic knowledge

Agents need knowledge in order to perform well. Some of that knowledge is
technical, some is organizational, and some is business-specific.

The challenge is deciding how to give knowledge to agents without flooding every
session with every document.

There are different levels of knowledge sharing:

- simple project instructions
- reusable skills
- local documentation
- business knowledge bases
- retrieval tools
- domain-specific sub-agents

The more complex the organization, the more important this becomes.

## Skills make workflows repeatable

A skill is a reusable way to teach an agent a workflow, a tool, a process, or a
domain-specific pattern.

A skill can contain instructions, examples, scripts, templates, checklists,
reference documents, tool usage guidance, and expected output formats.

The purpose of a skill is repeatability. Instead of rewriting the same long
prompt every time, you package the workflow so the agent can execute it
consistently.

Examples:

- how to create a pull request in your organization
- how to interact with Jira
- how to investigate a failing pipeline
- how to generate release notes
- how to update API documentation
- how to review code against team standards
- how to create a new module in a specific repository

The best way to create a skill is not to write it before you understand the
work. First, do the task manually with the agent several times. Notice what
instructions you repeat, what the model misunderstands, what examples help, what
files it needs, and what output format works best.

Then turn that repeated workflow into a skill.

A skill should include:

- when to use it
- when not to use it
- required inputs
- required context
- step-by-step workflow
- tools the agent should use
- files or docs the agent should inspect
- verification steps
- expected final output

A skill is not a one-off prompt. It should be refined and optimized over time.

## Business knowledge is part of engineering

Technical instructions are not enough. Many of the most important engineering
decisions depend on business knowledge:

- customer types
- pricing rules
- compliance requirements
- domain vocabulary
- product behavior
- support policies
- operational constraints
- legal or security requirements
- internal ownership boundaries

If this knowledge is not available to the agent, it will guess. Sometimes that
guess will look reasonable and still be wrong.

Business knowledge should be explicit, discoverable, and linked to the workflows
that need it.

The simplest approach is to keep specific documentation in the repository or in
a connected documentation repository:

- `docs/domain.md`
- `docs/architecture.md`
- `docs/testing.md`
- `docs/release-process.md`
- `docs/business-rules.md`
- `docs/api-contracts.md`

This works well when the knowledge is stable and not too large.

Good documentation for agents has short sections, concrete examples,
source-of-truth statements, clear ownership, links to related files, update
dates when relevant, and explicit "do" and "do not" rules.

For complex domains, simple docs may not be enough. You may need a domain
knowledge sub-agent.

This sub-agent's job is not to write code. Its job is to retrieve, filter, and
explain domain knowledge for the main agent. The main agent asks focused
questions:

- "What is the source-of-truth rule for refund eligibility?"
- "Which document defines the onboarding flow?"
- "What are the compliance constraints for storing this field?"
- "Which service owns this business concept?"

The domain sub-agent returns a concise answer with sources. The coding agent
then uses that answer as context for implementation.

## Knowledge wikis

Andrej Karpathy has described the idea of a knowledge wiki as a compact, curated
source of truth for agents. The practical idea is simple: instead of expecting
models to rediscover project knowledge every time, maintain a small set of
high-value documents that explain the system.

A useful agent knowledge wiki might contain:

- repository overview
- architecture map
- key business concepts
- service ownership
- common workflows
- testing strategy
- deployment model
- important decisions
- glossary
- known pitfalls

This is not a replacement for full documentation. It is an index and orientation
layer. It helps an agent know where to look and what matters.

## From vibe coding to engineering discipline

Vibe coding is useful for exploration. It helps you move fast, prototype, and
discover possibilities. But it becomes dangerous when it is used as the default
mode for production engineering.

Agentic engineering adds discipline:

- clear task definition
- small context
- focused tools
- reusable skills
- spec-driven planning
- sub-agent specialization
- source-of-truth documentation
- verification after each step
- human judgment for product and risk decisions

The model can generate code. The engineer still owns the outcome.

That is the core principle.

Use agents as powerful collaborators, not autonomous owners. Give them the
context they need, constrain the work, verify the result, and improve the
workflow over time.

That is how you move from vibe coding to agentic engineering.
